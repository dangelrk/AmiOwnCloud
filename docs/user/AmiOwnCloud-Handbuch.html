1. Einführung

AmiOwnCloud verbindet AmigaOS 3.x mit einem ganz normalen ownCloud- oder Nextcloud-Server. Die Verbindung läuft über WebDAV (HTTPS) – dieselbe Schnittstelle, die auch die offiziellen Clients unter Windows, macOS und Linux benutzen. Der Server selbst gehört nicht zu AmiOwnCloud; man braucht nur ein Konto darauf.

Es gibt zwei unabhängige Wege, den Server zu nutzen. Beide können gleichzeitig installiert sein:

WerkzeugArbeitsweisePasst für
OWNCLOUD:-Handler
Einstellungen: AmiOwnCloudPrefs		 Der Server wird zum Laufwerk OWNCLOUD:. Jeder Zugriff (Dir, Copy, Delete, Workbench-Fenster …) geht direkt an den Server. Keine lokale Kopie – ohne Netz geht nichts. schnellen Zugriff auf den ganzen Server
AmiOwnCloudSync (Commodity)
Einstellungen: AmiOwnCloudSyncPrefs		 Gleicht Paare aus einem lokalen Amiga-Ordner und einem Ordner auf dem Server ab – automatisch alle paar Minuten oder auf Knopfdruck. Die Dateien liegen lokal und sind auch offline verfügbar. Ordner, mit denen man regelmäßig arbeitet

Dazu kommen zwei Shell-Befehle, die es auch für macOS, Linux und (ungetestet) Windows gibt:

  • amiowncloud-sync – einmaliger Abgleich eines Ordnerpaares, z. B. zum Ausprobieren
  • amiowncloud-synctest – automatische Testreihe gegen einen echten Server

Jedes Programm hat seine eigene Konfigurationsdatei mit eigenen Zugangsdaten (siehe Konfiguration).

┌────────────────────────┐   WebDAV / HTTPS   ┌──────────────────────────┐
│ Amiga                  │  PROPFIND, GET,    │ ownCloud / Nextcloud     │
│  OWNCLOUD:-Handler     │◄──────────────────►│ (fremdbetrieben, nicht   │
│  AmiOwnCloudSync          │  PUT, MKCOL, MOVE, │  Teil von AmiOwnCloud)   │
│  amiowncloud-sync            │  DELETE, PROPPATCH │                          │
└────────────────────────┘                    └──────────────────────────┘

AmiOwnCloud ist Teil einer Projektfamilie: AmiCloud (eigener Server), AmiVCS (Versionsverwaltung) und die gemeinsame Bibliothek AmiCloudCore. Mit dem eigenen AmiCloud-Server hat AmiOwnCloud nichts zu tun.

2. Voraussetzungen

Amiga

  • AmigaOS 3.x, Prozessor 68020 oder besser (seit 0.2). Die Programme sind für kleine Systeme ausgelegt (GadTools statt MUI).
  • Ein TCP/IP-Stack mit bsdsocket.library (Version 4 oder neuer), z. B. Roadshow, AmiTCP/Genesis oder Miami. Er muss laufen, bevor ein Programm auf den Server zugreift.
  • AmiSSL 5 (amisslmaster.library). Wird von allen Programmen gebraucht, die mit dem Server sprechen – auch bei http://-Adressen.
  • MUI wird nicht gebraucht. Die Oberflächen verwenden intuition, gadtools und commodities.library aus dem Betriebssystem.
  • Stack: nichts einzustellen. Die Programme fordern selbst 64 KB an, der Handler bekommt seinen Stack aus dem DOSDriver (16 KB).
  • Speicher: Zum Ändern lädt der OWNCLOUD:-Handler eine Datei komplett ins RAM; für große Dateien entsprechend viel freien Speicher einplanen. Reines Lesen holt nur die gelesenen Teile.

Server

  • Ein Konto auf einem ownCloud- oder Nextcloud-Server.
  • Empfohlen: ein eigenes App-Passwort für den Amiga (in Nextcloud unter Einstellungen → Sicherheit), nicht das Login-Passwort.
  • HTTPS mit gültigem Zertifikat. Die Zertifikatsprüfung lässt sich zum Testen abschalten (verify_ssl=0), sollte aber an bleiben.

PC

Nur amiowncloud-sync/amiowncloud-synctest: macOS oder Linux mit libcurl, Windows ungetestet – siehe Installation am PC.

Archiv auspacken, z. B. LhA x AmiOwnCloud-0.2.lha RAM:.

Alle Teile haben Workbench-Icons. Zum Installieren in der Schublade das Icon Install-AmiOwnCloud doppelt anklicken. Es startet den Commodore-Installer (bei AmigaOS 3.2 in SYS:System, bei älteren Systemen von der Install-Diskette nach C: kopieren). Ohne Installer gibt es dasselbe als Shell-Skript:

CD RAM:AmiOwnCloud
Execute Install-AmiOwnCloud.shell

Aktualisieren: Eine neuere Version installiert man genauso – Archiv auspacken, Installer erneut starten. Er vergleicht bei jedem Programm die installierte Version mit der im Archiv. Als Einsteiger oder Geübter Benutzer ersetzt er gleiche und ältere Versionen; eine neuere installierte Version bleibt stehen und wird am Ende genannt. Im Expertenmodus zeigt er bei jedem schon installierten Programm beide Versionen und fragt. Vorhandene Icons (mit eigenen Tooltypes und Positionen) bleiben erhalten. Die Shell-Variante fragt nur nach, wenn ein installiertes Programm neuer ist als das im Archiv. Ist OWNCLOUD: schon gemountet, arbeitet es bis zum nächsten Neustart mit der alten Version weiter.

Das Skript fragt, welche Teile installiert werden sollen (im Installer per Auswahlliste, im Shell-Skript mit y oder n):

  • OWNCLOUD:-Handler und AmiOwnCloudPrefs. Wahlweise wird der DOSDriver nach DEVS:DOSDrivers (Mount bei jedem Systemstart) oder nach SYS:Storage/DOSDrivers (Mount nur von Hand) kopiert. Gibt es noch keine amiowncloud.cfg, bietet es an, AmiOwnCloudPrefs sofort zu starten, und danach, OWNCLOUD: gleich zu mounten.
  • AmiOwnCloudSync (nach SYS:Tools/Commodities) und AmiOwnCloudSyncPrefs (nach SYS:Prefs). Bietet an, AmiOwnCloudSyncPrefs sofort zu starten, und auf Wunsch eine Startzeile in S:User-Startup einzutragen.
  • amiowncloud-sync und amiowncloud-synctest nach C:, auf Wunsch mit einer Beispiel-Konfiguration ENVARC:amiowncloud-sync.cfg.
  • Das Handbuch wird nach HELP: kopiert, wenn HELP: zugewiesen ist.
Nichts wird überschrieben
Vorhandene Konfigurationsdateien in ENV:/ENVARC: und ein vorhandener DOSDriver werden nie überschrieben. Eine Neuinstallation über eine alte Version ist also gefahrlos.

Wie es danach weitergeht:

  • Laufwerk: AmiOwnCloudPrefs ausfüllen, Speichern, dann in der Shell Mount OWNCLOUD: (bzw. bei Ablage in SYS:Storage: Mount SYS:Storage/DOSDrivers/OWNCLOUD)
  • Ordnerabgleich: AmiOwnCloudSyncPrefs ausfüllen, Speichern, dann AmiOwnCloudSync starten.

Die Programme haben keine eigenen Piktogramme (.info). Aus der Workbench startet man sie mit „Fenster → Alle Dateien zeigen“ (dann erscheint ein Standard-Piktogramm) oder legt sich selbst eines an.

git clone --recurse-submodules https://github.com/dangelrk/AmiOwnCloud.git
cd AmiOwnCloud
make pc
sudo make install          # nach /usr/local/bin

6. Konfiguration

Jedes Werkzeug hat seine eigene Datei – auch wenn alle auf denselben Server zeigen, teilen sie sich keine Zugangsdaten:

Dateigelesen vongeschrieben von
amiowncloud.cfgamiowncloud-worker (OWNCLOUD:-Handler)AmiOwnCloudPrefs
AmiOwnCloudSync.cfgAmiOwnCloudSyncAmiOwnCloudSyncPrefs
amiowncloud-sync.cfgamiowncloud-sync, amiowncloud-synctestvon Hand

Beispiele liegen in der Schublade unter Examples/.

Format

Eine Einstellung pro Zeile: schluessel=wert. Leerzeichen um das = sind erlaubt, Zeilen mit # am Anfang sind Kommentare, unbekannte Schlüssel werden ignoriert. Gemeinsame Schlüssel:

SchlüsselBedeutung
serverNur der Hauptserver, z. B. https://cloud.example.com. Daraus wird automatisch https://cloud.example.com/remote.php/dav/files/<user> gebildet. Enthält der Wert schon /remote.php/, wird er unverändert benutzt.
userBenutzername (auch username)
passPasswort (auch password), am besten ein App-Passwort
verify_ssl1 = TLS-Zertifikat prüfen (Standard), 0 = nicht prüfen (nur für Tests)

Die Dateien enthalten das Passwort im Klartext. ENV: und ENVARC: sind auf dem Amiga für jeden Prozess lesbar.

ENV: und ENVARC: – Benutzen, Speichern, Abbrechen

KnopfWirkung
Benutzenschreibt nur nach ENV: (RAM) – wirkt sofort, ist nach einem Neustart wieder weg
Speichernschreibt nach ENVARC: und ENV: – wirkt sofort und dauerhaft
Abbrechenschreibt nichts

Beim Systemstart kopiert AmigaOS ENVARC: nach ENV:. Beide Prefs-Programme zeigen beim Start den Inhalt von ENV: (ersatzweise ENVARC:); weichen beide voneinander ab, meldet die Statuszeile „ENV:/ENVARC: unterscheiden sich (angezeigt: ENV:)“.

Kommentare gehen verloren
Die Prefs-Programme schreiben die Datei jedesmal komplett neu. Kommentare und von Hand ergänzte Zeilen gehen dabei verloren – insbesondere schreibt AmiOwnCloudSyncPrefs keine debug=-Zeile.

amiowncloud.cfg – Einstellungen für OWNCLOUD:

Ort: ENV:amiowncloud.cfg, dauerhaft ENVARC:amiowncloud.cfg. Gelesen von amiowncloud-worker, nur aus ENV: und nur einmal beim Mounten. Editor: AmiOwnCloudPrefs.

server=https://cloud.example.com
user=bob
pass=geheim
verify_ssl=1
basepath=/
debug=
gmt_offset=60
dst=0
#timeout=120
#cache_ttl=30
SchlüsselBedeutungStandard
basepathOrdner auf dem Server, der als Wurzel von OWNCLOUD: erscheint, z. B. /Amiga/
debugDatei, in die amiowncloud-worker jede HTTP-Anfrage und -Antwort schreibt, z. B. T:amiowncloud.logleer = aus
gmt_offsetAbstand der Ortszeit zu UTC in Minuten (MEZ = 60). Die Amiga-Uhr kennt keine Zeitzone; ohne diesen Wert stimmen die Dateizeiten um die Zeitzone nicht.0
dst1 = Sommerzeit aktiv (eine Stunde mehr). Muss bei der Zeitumstellung von Hand angepasst werden.0
timeoutNetz-Timeout in Sekunden: so lange darf eine Verbindung ganz ohne Datenfluss bleiben. Die Dauer einer Übertragung ist nie begrenzt – eine große Datei über ein Modem läuft, solange Daten fließen. Gilt auch für AmiOwnCloudSync und amiowncloud-sync.120
cache_ttlWie viele Sekunden eine Verzeichnisliste zwischengespeichert wird; über ein Modem lohnen 120 bis 300.30

Wichtig: Der Worker liest die Datei nur einmal beim Start. Weil der Handler nicht ausgehängt werden kann, wirken Änderungen zuverlässig erst nach einem Neustart des Amiga.

AmiOwnCloudSync.cfg – Profil und Ordnerpaare

Ort: ENV:AmiOwnCloudSync.cfg, dauerhaft ENVARC:AmiOwnCloudSync.cfg. Gelesen von AmiOwnCloudSync – ENV: zuerst, sonst ENVARC:; gibt es keine von beiden, ist das der erste Start und alles bleibt leer. Editor: AmiOwnCloudSyncPrefs.

server=https://cloud.example.com
user=bob
pass=geheim
verify_ssl=1
interval=15
pair=Work:Dokumente|/Dokumente|on
pair=Work:Projekte|/Projekte|off
SchlüsselBedeutung
intervalMinuten zwischen zwei automatischen Abgleichen, Standard 15. 0 oder negativ = kein Autosync. Ob der Autosync läuft, entscheidet sich beim Start der Commodity; eine geänderte Minutenzahl gilt ab dem nächsten Zyklus.
pairpair=<lokal>|<remote>|<on/off> – ein Ordnerpaar, beliebig oft. lokal: Amiga-Pfad, zugleich Name in der Liste; remote: Ordner relativ zur Dateisammlung, / = die ganze Cloud; on/off: aktiv oder pausiert (1/0 geht auch).
debugNur von Hand: Datei für HTTP-Protokoll und Fehlerdetails, z. B. T:AmiOwnCloudSync.log (siehe Fehlersuche)

Die Commodity liest die Datei beim Start, beim Öffnen des Fensters, vor jedem Autosync und bei „Neu laden“ neu. Nach „Benutzen“ oder „Speichern“ ist also kein Neustart der Commodity nötig (Ausnahme: Autosync ein- oder ausschalten).

amiowncloud-sync.cfg – Einstellungen für die Shell-Befehle

Gelesen von amiowncloud-sync und amiowncloud-synctest, wenn keine Datei mit -c angegeben ist:

SystemDatei

7. Der OWNCLOUD:-Handler Amiga

Der Handler macht den Server zum Laufwerk OWNCLOUD:; auf der Workbench erscheint es als Volume „OwnCloud“. Er besteht aus zwei Programmen in L::

  • amiowncloud-handler – der eigentliche DOS-Handler
  • amiowncloud-worker – erledigt alle Netzwerkzugriffe; wird vom Handler beim Mounten als L:amiowncloud-worker gestartet

Einrichten

  1. AmiOwnCloudPrefs starten, Server, Benutzer und Passwort eintragen, Speichern.
  2. In der Shell: Mount OWNCLOUD: (liegt der DOSDriver in DEVS:DOSDrivers, geschieht das bei jedem Systemstart automatisch; liegt er in SYS:Storage/DOSDrivers: Mount SYS:Storage/DOSDrivers/OWNCLOUD).
  3. Testen: Dir OWNCLOUD:

Der DOSDriver DEVS:DOSDrivers/OWNCLOUD:

Handler   = L:amiowncloud-handler
StackSize = 16384
Priority  = 5
GlobVec   = -1
Activate  = 1

Beim Mounten während des Bootens muss das Netz noch nicht laufen: der Worker baut die Verbindung erst beim ersten echten Zugriff auf.

Was geht

  • Verzeichnisse anzeigen (Dir, List, Workbench-Fenster)
  • Dateien lesen und schreiben (Copy, Type, Editoren …)
  • Verzeichnisse anlegen (MakeDir)
  • Löschen (Delete, auch Delete … ALL)
  • Umbenennen und Verschieben innerhalb von OWNCLOUD: (Rename)
  • Datum setzen (SetDate) – nur wenn der Server das unterstützt (ownCloud/Nextcloud tun das)
  • Info OWNCLOUD:

Was nicht geht bzw. anders ist

  • Protect und FileNote melden Erfolg, werden aber nicht gespeichert. WebDAV kennt keine Amiga-Schutzbits und keine Dateikommentare. So scheitern Workbench-Kopien nicht; der Wert ist aber beim nächsten Auflisten wieder weg.
  • Info OWNCLOUD: zeigt eine feste Platzhalter-Größe (etwa 2 GB, halb voll), nicht den echten Platz auf dem Server.
  • Gelesen werden nur die Teile einer Datei, die ein Programm wirklich liest; bei „Alle Dateien anzeigen“ kostet eine Datei ohne Icon 4 KB. Zum Ändern wird eine Datei ganz ins RAM geladen und erst beim Schließen hochgeladen.
  • Immer nur eine Server-Anfrage zur Zeit. Während eine große Datei übertragen wird, beantwortet OWNCLOUD: trotzdem alles, was ohne Server geht (Info, Lesen und Schreiben geöffneter Dateien, frisch gelesene Verzeichnisse); alles andere wartet.
  • Fließen timeout Sekunden lang (Standard 120) keine Daten oder bricht die Verbindung ab, scheitert der Zugriff mit „No disk present“; DOS bietet Wiederholen an. Abgebrochene Downloads setzt der Worker an der Abbruchstelle fort. Break auf amiowncloud-worker bricht eine laufende Übertragung ab.
  • Scheitert beim Schließen einer geänderten Datei das Hochladen, meldet Close() einen Fehler, und der Inhalt liegt in T:AmiOwnCloud-unsaved/.
  • Der Handler lässt sich nicht aushängen. Zum Entfernen und nach Änderungen an amiowncloud.cfg: neu starten.
  • Verzeichnislisten werden 30 Sekunden zwischengespeichert (cache_ttl). Was ein anderes Gerät auf dem Server ändert, erscheint entsprechend verzögert.
  • Keine Prüfsummen bei Up- und Download (WebDAV liefert keine).

Fehlersuche

  • Kommt bei jedem Zugriff ein Fehler, zuerst ENV:amiowncloud.cfg prüfen: ohne Datei startet der Worker zwar, aber jede Anfrage scheitert.
  • debug=T:amiowncloud.log in amiowncloud.cfg schreibt jede HTTP-Anfrage mit (wirkt nach dem nächsten Neustart).
  • Type OWNCLOUD:debuglog zeigt ein internes Protokoll der Nachrichten zwischen Handler und Worker.

Technische Einzelheiten: handler/owncloudhandler/README.md in den Quellen.

9. AmiOwnCloudSync – die Commodity Amiga

AmiOwnCloudSync gleicht Ordnerpaare (lokaler Amiga-Ordner ↔ Ordner auf dem Server) im Hintergrund ab. Sie meldet sich als Commodity an und erscheint in Exchange (SYS:Tools/Commodities/Exchange) als „AmiOwnCloudSync“ mit der Beschreibung „OwnCloud-Ordnerabgleich“. Vorher einrichten: AmiOwnCloudSyncPrefs.

Starten

StartHotkey festlegen
Workbench (Piktogramm, sofern angelegt)Tooltype CX_POPKEY=ctrl alt a
Shell: Run >NIL: SYS:Tools/Commodities/AmiOwnCloudSyncOption -k "ctrl alt s"

Ohne Angabe gilt der Hotkey ctrl alt a. Andere Tooltypes oder Optionen gibt es nicht. Ohne Run blockiert das Programm die Shell, bis es beendet wird.

Nach dem Start

  • Die Commodity läuft ohne Fenster im Hintergrund.
  • Ist interval größer 0, gleicht sie alle interval Minuten alle aktiven Paare ab (der erste Abgleich kommt nach Ablauf des ersten Intervalls, nicht sofort beim Start).
  • Der Hotkey blendet das Ordnerpaar-Fenster ein und aus.
  • Wird AmiOwnCloudSync ein zweites Mal gestartet, beendet sich die zweite Kopie, und die laufende zeigt ihr Fenster.

Exchange

ExchangeWirkung
Anzeigen / VerbergenFenster ein- bzw. ausblenden
Aktivieren / DeaktivierenHotkey an/aus
EntfernenAmiOwnCloudSync beenden

Beenden geht außerdem mit Ctrl-C an den Prozess (z. B. Break).

Netz muss laufen
Beim Start müssen sich bsdsocket.library und AmiSSL 5 öffnen lassen. Sonst zeigt die Commodity einen Requester mit der Ursache (z. B. cannot open bsdsocket.library) und beendet sich, ebenso bei einem ungültigen Hotkey (CX_POPKEY). Beim automatischen Start also erst den TCP/IP-Stack starten. Läuft AmiOwnCloudSync bereits, öffnet ein zweiter Start nur das Fenster der laufenden Commodity.

10. Das Ordnerpaar-Fenster

Das Fenster zeigt die Ordnerpaare nur an; bearbeitet werden sie in AmiOwnCloudSyncPrefs.

ElementWirkung
Listealle Paare als * lokal -> remote; * = aktiv, Leerzeichen = pausiert
Jetzt syncengleicht das ausgewählte Paar ab
Alle syncengleicht alle Paare nacheinander ab (pausierte werden übersprungen)
Neu ladenliest AmiOwnCloudSync.cfg sofort neu – z. B. nachdem in AmiOwnCloudSyncPrefs gespeichert wurde, während das Fenster offen war
Statuszeilewährend des Abgleichs Fortschritt je Datei (Prozent und KB/s), danach das Ergebnis, z. B. Work:Dokumente: 3 hoch, 2 runter, 0 Konflikt(e); bei Problemen mit „, Fehler!“ am Ende
Menü Projekt → Info…kurze Programminfo in der Statuszeile
Menü Projekt → Beenden, Schließsymbolblendet nur das Fenster aus – die Commodity läuft weiter; ganz beenden über Exchange

Fehlen Server, Benutzer oder Passwort, meldet die Statuszeile „Profil unvollstaendig (Server/Benutzer/Passwort)“.

Abgleich blockiert das Fenster
Der Abgleich läuft im selben Prozess. Solange er dauert, reagiert das Fenster nicht auf Knöpfe, und auch Hotkey und Exchange werden erst danach bearbeitet. Bei großen Ordnern kann das dauern.

Hinzufügen/Bearbeiten öffnet ein kleines Fenster mit Lokaler Pfad (z. B. Work:Dokumente, von Hand eintippen – es gibt keinen Dateiauswahl-Requester), Remote-Pfad (z. B. /Dokumente, / = die ganze Cloud), Aktiv und OK/Abbrechen.

Eine laufende AmiOwnCloudSync übernimmt die neuen Werte beim nächsten Öffnen ihres Fensters, beim nächsten Autosync oder mit „Neu laden“ – ohne Neustart. Eine von Hand eingetragene debug=-Zeile geht beim Speichern verloren.

12. So funktioniert der Abgleich

AmiOwnCloudSync und amiowncloud-sync benutzen denselben Zwei-Wege-Abgleich. Für jedes Ordnerpaar merkt er sich den Stand nach dem letzten erfolgreichen Abgleich in der Datei .amicloudsync im lokalen Ordner (nicht löschen, solange das Paar benutzt wird). Durch den Vergleich „lokal – Server – letzter Stand“ erkennt er:

SituationAktion
neue Datei auf einer Seitewird auf die andere kopiert
Datei lokal geändertUpload
Datei auf dem Server geändertDownload
Datei auf einer Seite gelöschtwird auch auf der anderen Seite gelöscht
neues Verzeichniswird auf der anderen Seite angelegt

Konflikte

  • Datei seit dem letzten Abgleich auf beiden Seiten geändert
  • Datei auf einer Seite gelöscht, auf der anderen geändert
  • Datei auf der einen, Verzeichnis gleichen Namens auf der anderen Seite

Ein Konflikt wird nur gemeldet („1 Konflikt(e)“), keine Seite wird überschrieben. Auflösen: die unerwünschte Fassung löschen oder umbenennen und erneut abgleichen.

Erster Abgleich eines Paares
Es gibt noch keinen gemerkten Stand, und WebDAV liefert keine Prüfsummen. Liegt eine Datei mit gleichem Namen schon auf beiden Seiten, kann der Abgleich nicht feststellen, ob sie gleich ist, und meldet einen Konflikt. Deshalb am besten mit einem leeren lokalen Ordner (alles wird heruntergeladen) oder einem leeren Server-Ordner (alles wird hochgeladen) beginnen. Gefahrlos ausprobieren: amiowncloud-sync -n <lokal> <remote>.

Schutz vor Datenverlust (ab 0.2)

  • Kann ein Ordner auf einer Seite nicht gelesen werden (Netzfehler, gesperrter Ordner), bricht der Abgleich ab, bevor er etwas ändert.
  • Ctrl-C bricht nach der laufenden Übertragung ab. Ein abgebrochener Abgleich löscht nichts; der nächste macht den Rest.
  • Ist der Ordner auf dem Server verschwunden (etwa umbenannt), wird er nicht leer neu angelegt; der Abgleich bricht ab.
  • Gehört .amicloudsync zu einem anderen Server, Benutzer oder Server-Ordner, wird der Stand verworfen. Der Abgleich führt dann nur zusammen und löscht nichts.
  • Ein Ordner wird nur gelöscht, wenn auch alles darin gelöscht wird. Liegt darin etwas Neues, wird er wieder angelegt.
  • Dateien, die während des Abgleichs geändert werden, werden weder überschrieben noch gelöscht.
  • Hochgeladen wird nur, wenn die Datei auf dem Server noch die beim Abgleich gesehene ist. Sonst wird ein Konflikt gemeldet.
  • Namen, die sich nur in Groß-/Kleinschreibung unterscheiden, und Namen, die für das Dateisystem zu lang sind (klassisches FFS: 30 Zeichen), werden übersprungen und gemeldet.
  • Nie abgeglichen werden .DS_Store, ._*, Thumbs.db, desktop.ini, ~$*, *.part sowie Namen mit Backslash oder Steuerzeichen.

Lokale Dateien bekommen die Ortszeit nach gmt_offset und dst aus der Konfigurationsdatei (die Sommerzeit wird von Hand umgestellt).

13. amiowncloud-sync Amiga + PC

amiowncloud-sync [optionen] <lokales-verzeichnis> <remote-verzeichnis>

Gleicht ein Ordnerpaar einmal ab (derselbe Abgleich wie in AmiOwnCloudSync, siehe So funktioniert der Abgleich) und beendet sich. Praktisch zum Ausprobieren einer Verbindung oder für eigene Skripte.

OptionBedeutung
-s <url>Server: Hauptserver (https://cloud.example.com) oder volle WebDAV-Adresse (https://cloud.example.com/remote.php/dav/files/bob)
-u <user>Benutzername
-p <pass>Passwort (am besten ein App-Passwort)
-c <datei>Konfigurationsdatei statt der Standarddatei (siehe amiowncloud-sync.cfg)
-kTLS-Zertifikat nicht prüfen (nur für Tests)
-nProbelauf: zeigt, was passieren würde, ändert nichts
--helpKurzhilfe

Die Optionen müssen vor den beiden Verzeichnissen stehen. Server, Benutzer und Passwort müssen angegeben sein (Option oder Datei).

# Amiga
amiowncloud-sync -n Work:Dokumente /Dokumente
amiowncloud-sync Work:Dokumente /Dokumente
amiowncloud-sync -s https://cloud.example.com -u bob -p geheim RAM:Test /Test

# macOS/Linux
amiowncloud-sync ~/Amiga/Dokumente /Dokumente

Rückgabewert: 0 = alles in Ordnung, 1 = Fehler (Aufruf, Netz oder einzelne Dateien). Konflikte allein gelten nicht als Fehler. Hinweis: mit -p steht das Passwort in der Shell-Historie – besser die Konfigurationsdatei benutzen.

14. amiowncloud-synctest Amiga + PC

amiowncloud-synctest [optionen] <lokaler-testordner> <remote-testordner>

Prüft den Abgleich automatisch gegen einen echten Server; läuft auf Amiga und PC gleich. Optionen wie bei amiowncloud-sync (-s, -u, -p, -c, -k, --help; kein -n), dieselbe Konfigurationsdatei (amiowncloud-sync.cfg).

Achtung
Der Remote-Testordner wird zu Beginn gelöscht, benutzt und am Ende wieder gelöscht – einen Namen wählen, den es auf dem Server nicht gibt, z. B. /WebdavSyncTest. Im lokalen Testordner legt das Programm note1.txt, sub/note2.txt und .amicloudsync an und löscht sie am Ende wieder; einen leeren Ordner verwenden.
amiowncloud-synctest RAM:synctest /WebdavSyncTest
PrüfungInhalt
T1erster Abgleich lädt beide neuen Dateien hoch
T2zweiter Abgleich überträgt nichts
T3a / T3blokale Änderung → genau ein Upload; danach stabil
T4 (Vorbereitung)Datei direkt auf dem Server ändern
T4a / T4b / T4cÄnderung auf dem Server → genau ein Download; Inhalt stimmt; danach stabil
T5a / T5b / T5clokales Löschen wird übertragen; Datei ist auf dem Server weg; danach stabil
T6a / T6b / T6cÄnderung auf beiden Seiten → Konflikt; lokale Datei und Server-Datei unverändert

Insgesamt 14 Prüfungen. Jede meldet [PASS] oder [FAIL], am Ende „n passed, m failed“. Rückgabewert 0 = alle bestanden, 1 = mindestens eine fehlgeschlagen.

15. Fehlersuche

Programm startet nicht oder beendet sich sofort

TCP/IP-Stack gestartet? AmiSSL 5 installiert (LIBS:amisslmaster.library)? Die Shell-Befehle melden dann „network initialisation failed“ bzw. „cannot open amisslmaster.library (AmiSSL 5 required)“.

Anmeldung scheitert

Benutzername und Passwort prüfen. Bei Nextcloud mit Zwei-Faktor-Anmeldung ist ein App-Passwort Pflicht. Adresse prüfen: mit einem Webbrowser am PC muss https://cloud.example.com/remote.php/dav/files/<user>/ nach Anmeldung erreichbar sein.

Zertifikatsfehler

Die Systemuhr des Amiga muss stimmen, und AmiSSL braucht aktuelle Stammzertifikate. Nur zum Testen: verify_ssl=0 bzw. -k.

Verbindung testen

Zuerst mit amiowncloud-sync -n einen Probelauf machen oder amiowncloud-synctest laufen lassen – beide geben Fehler direkt in der Shell aus.

OWNCLOUD: meldet bei jedem Zugriff einen Fehler

ENV:amiowncloud.cfg vorhanden und vollständig? Nach Änderungen neu starten (der Worker liest die Datei nur beim Start). Protokoll: debug=T:amiowncloud.log in amiowncloud.cfg, Neustart, Zugriff wiederholen, dann Type T:amiowncloud.log. Zusätzlich Type OWNCLOUD:debuglog.

OWNCLOUD: reagiert nicht mehr

Eine Anfrage scheitert erst, wenn timeout Sekunden (Standard 120) gar keine Daten fließen; bis dahin wartet ein Zugriff, der den Server braucht. Break auf amiowncloud-worker bricht die laufende Übertragung sofort ab. Netzwerk prüfen.

Langsame Verbindung (Modem), Übertragungen brechen ab

Alle Timeouts greifen nur bei Stillstand. Bricht es trotzdem ab, timeout=300 setzen. Abgebrochene Downloads werden fortgesetzt, nicht neu begonnen. Ctrl-C bricht amiowncloud-sync ab, Break auch AmiOwnCloudSync. Für OWNCLOUD: lohnt cache_ttl=300.

AmiOwnCloudSync meldet „… Fehler!“, aber nicht welcher

Die Commodity hat keine eigene Konsole. In ENV:AmiOwnCloudSync.cfg (und ENVARC:) von Hand eine Zeile debug=T:AmiOwnCloudSync.log ergänzen, im Fenster „Neu laden“ klicken, erneut abgleichen, dann Type T:AmiOwnCloudSync.log. Das Protokoll enthält jede HTTP-Anfrage mit Status und je Fehler die betroffene Datei. T: liegt in der RAM-Disk; für ein dauerhaftes Protokoll einen Pfad auf einer Festplatte angeben. Achtung: Speichern in AmiOwnCloudSyncPrefs entfernt die Zeile wieder.

„Profil unvollstaendig“

Server, Benutzer oder Passwort fehlen in AmiOwnCloudSync.cfg – in AmiOwnCloudSyncPrefs eintragen und Speichern.

AmiOwnCloudSync erscheint nicht in Exchange

Läuft das Programm (Status in der Shell)? Wurde es gestartet, bevor das Netz lief, hat es sich sofort beendet.

Hotkey reagiert nicht

Kollidiert die Tastenkombination mit einer anderen Commodity? Anderen Hotkey mit CX_POPKEY bzw. -k wählen. Während eines Abgleichs werden Hotkeys erst danach bearbeitet.

Viele Konflikte beim ersten Abgleich

Siehe So funktioniert der Abgleich: gleichnamige Dateien auf beiden Seiten ohne gemerkten Stand gelten als Konflikt.

Falsche Dateizeiten auf OWNCLOUD:

gmt_offset und dst in amiowncloud.cfg setzen.

16. Bekannte Grenzen

OWNCLOUD:-Handler

  • Schutzbits und Dateikommentare werden nicht gespeichert.
  • Info zeigt keine echte Belegung.
  • Zu ändernde Dateien liegen komplett im RAM.
  • Eine Server-Anfrage zur Zeit; Timeout nur bei Stillstand.
  • Kein Aushängen; Konfigurationsänderungen erst nach Neustart.

AmiOwnCloudSync

  • Der Abgleich läuft im selben Prozess; das Fenster ist solange blockiert.
  • Ein Server-Profil für alle Ordnerpaare (kein Betrieb mit mehreren Konten).
  • Pfade werden in AmiOwnCloudSyncPrefs von Hand eingetippt (kein Dateiauswahl-Requester).
  • WebDAV hat keinen Änderungszähler: jeder Abgleich liest den ganzen Remote-Ordner ein (bei sehr großen Ordnern entsprechend langsam).
  • Beim ersten Abgleich gelten gleichnamige Dateien auf beiden Seiten als Konflikt.

Allgemein

  • Keine Piktogramme (.info) für die Programme.
  • Auf echter Amiga-Hardware sind nicht alle Wege gleich gut erprobt; entwickelt und getestet wurde überwiegend im Emulator.

17. Deinstallation

Execute Uninstall-AmiOwnCloud

(in der Installationsschublade). Das Skript löscht die Programme, den DOSDriver und das Handbuch in HELP: und fragt, ob auch die Einstellungen (amiowncloud.cfg, AmiOwnCloudSync.cfg, amiowncloud-sync.cfg in ENV:/ENVARC:) gelöscht werden sollen. Vorher AmiOwnCloudSync über Exchange beenden. Von Hand bleibt zu tun:

  • einen AmiOwnCloudSync-Block in S:User-Startup entfernen (;BEGIN AmiOwnCloudSync … ;END AmiOwnCloudSync)
  • nicht mehr benötigte .amicloudsync-Dateien in den lokalen Ordnern der Ordnerpaare löschen
  • neu starten, damit ein gemounteter OWNCLOUD:-Handler verschwindet

Auf dem Server wird nichts gelöscht. Am PC: die Programme aus /usr/local/bin (bzw. dem gewählten PREFIX) und ~/.amiowncloud-syncrc löschen.
